## Companion state files

None at the moment. A companion file has no `restore` block and holds state a routine
reads, such as the stable URL of an Artifact it republishes. The script neither writes
nor prunes them.

## Retired

`retired/` holds backups of routines that are no longer on the account. The script moves
them there rather than deleting them, so a restore block is never lost to a routine
being turned off. As of 2026-10-07 it holds:

- `chess-weekly-review.json` and its state file `chess-weekly-review-artifact.json`
- `first-light-brief-hourly.json`, its state file `first-light-brief-artifact.json`, and
  the docs `first-light-brief.md` and `throughline.md` (Throughline was shut down on
  2026-09-30)
- `weekly-rollup-dashboard-refresh.json`
- `weekly-task-review.json` (replaced by *Weekly Review*)

## Not backed up here

The two *Shared expenses* routines (mid-month update and month close) are on the account
but deliberately kept out of this public repo, because their prompts hold household
details. `format_routines.py` would write them if given the full `list_triggers` output,
so leave them out of its input.

**2026-09-12 — script fixed.** `format_routines.py` had drifted from what `list_triggers`
returns and was extracting an empty prompt from every routine, which is why the chess
routine had to be backed up by hand. Three fixes:

- It now reads the prompt from `derived_state.prompt`, falling back to
  `session_request.events[].payload.internal_anthropic_catchall.message.content`, with
  the old `job_config.ccr` path kept as a last resort.
- It no longer deletes files it does not own. The previous version pruned every `*.json`
  not matching a live routine — which would have deleted both companion state files
  above and broken the stable-URL mechanism they exist for.
- Backup filenames are now keyed to the trigger id, so renaming a routine updates its
  file in place instead of orphaning it and creating a second one.

Regenerating now reproduces the hand-written chess backup byte-for-byte apart from two
added informational fields, which is the check that the drift is actually closed.

> **Drift, 2026-09-02.** `list_triggers` returned **zero** routines on the account, and this
> file had not been regenerated since 23 August, so the control plane briefly versioned one dead
> routine and no live ones.
>
> Between 29 August and 2 September, two self-re-arming PR check-in routines fired 50+ times — each run
> creating a fresh one-shot about two hours out, watching draft PRs that could only change by hand. Both
> were deleted on 2 September along with the PRs they watched.
>
> When rebuilding any check-in routine, prefer a fixed cron or an event-driven Monitor over
> "re-arm silently if nothing changed" — that pattern has no stopping condition when the
> thing it watches only changes by hand.
